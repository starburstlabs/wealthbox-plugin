# Manage a Client Service Request

Turn a request into one tracked process — a source note, the right workflow or task set, explicit
owners and dates — then keep that same process current as the work moves.

## Quick start

```
User: "Process this client service request and set up the follow-through."
→ Identify client, household, request type, desired outcome, timing, and affected records
→ Check recent activity and open work: is this new, underway, or part of a broader issue?
→ Record the source note capturing what the client actually asked for
→ Propose the workflow (or a task set, if no firm process fits) with owners and due dates
→ On approval: create it, and draft the acknowledgment
```

## Workflow

1. **Identify the request and everything it touches** — client, household, request type, desired
   outcome, timing, source communication, and every affected record.

2. **Determine whether this is actually new.** Review recent Wealthbox activity and open work first.
   The request may already be underway, may be a follow-up to an open request, or may be one symptom
   of a broader issue. Classify it as new, already underway, or part of a broader issue, and say which.
   Getting this wrong creates parallel work, which is the failure mode that makes service tracking
   worthless.

3. **Retrieve external information only where the request depends on it** — custodial, planning, TAMP
   or alternatives, reporting, or meeting-note detail. Use it to understand the request and coordinate
   the work, not to answer operational questions from a stale CRM copy.

4. **Escalate rather than process anything involving movement of money or a compliance decision.**
   Requests to move funds, wire, transfer, change beneficiaries, or alter account registration are
   tracked here and **never executed**. Create the process, assign it to the right person, note what
   the client asked for — and do not draft a confirmation that implies the movement will happen. Say
   plainly that it requires the firm's own authorization path.

5. **Translate the request into a tracked process:**

   - a **source note** documenting what the client requested, in their terms;
   - a **workflow** when a defined firm process applies;
   - **assigned tasks** with owners, due dates, and dependencies — never an unassigned step;
   - related **events, opportunities, or record updates**;
   - **client communications** — an acknowledgment of receipt, and a progress update whenever the
     request reaches a milestone, stalls, or needs something from the client. Each one prepared as a
     draft.

6. **When no defined firm process applies, say so and offer a task set.** Do not fabricate a
   multi-step workflow to make the request look handled. A named task list with owners is honest and
   works; an invented workflow misrepresents the firm's process.

7. **Approval gate.** Present the proposed process — note, workflow or task set, owners, dates — before
   creating it. Approve client-facing steps individually.

8. **Track external and manual steps explicitly.** A step that happens in another system, on paper, or
   over the phone still gets a task with an owner and a date. Invisible steps are where service
   requests die.

9. **Update the existing request as information arrives.** Never create parallel work for the same
   request. Detect stalled dependencies, missing information, overdue steps, and unanswered questions,
   and surface them rather than waiting for someone to notice. Where the client is the one waiting, or
   is the one being waited on, draft the progress update that says so.

10. **On completion**, document the resolution, complete the associated Wealthbox work, and prepare a
    final client message — as a draft — summarizing the outcome and anything still resting with the
    client.

## Source authority

Wealthbox wins outright for the request record, the workflow, the tasks, and the history of what has
been done — and it is the only system this skill writes to. Account status, balances, and restrictions
belong to the custodial source; plan detail to the financial-planning source; product and liquidity
terms to the TAMP or alternatives source; what the client said to the meeting record and the source
communication. Never answer an operational question from a Wealthbox cache when the owning system is
connected; where it is not, say the answer is unverified and carry its as-of date.

## Approval gates

- **Never execute a financial transaction.** No transfers, wires, trades, or funds movement of any
  kind. Track the request, escalate it, and say explicitly that the skill cannot perform it.
- **Never confirm an action to a client that has not happened.** The acknowledgment says the request was
  received and what happens next — never that it is done.
- **Nothing is created before the proposed process is approved.**
- **Never send.** Every client message, including the final summary, is a draft.
- **Never close or complete work on inference.** Completion requires evidence or the user's word.
- **Never delete.** Superseded steps are cancelled with a reason, not removed.

## Degradation

With no external systems connected, still run the process end to end on Wealthbox: the note, the
workflow or task set, the owners, the tracking. Where a request depends on external detail that is
unavailable, create the task to obtain it and say so. Never guess an account fact into a client
acknowledgment.

## Never invent capability

No matching workflow template means a task set, stated as such. No field for a request attribute means
it goes in the note. Do not invent a firm process, an SLA, or a turnaround commitment the firm has not
defined — especially not in a client-facing draft.

## Example requests

- "Process this client service request and set up all of the follow-through in Wealthbox."
- "Turn this email into the correct service workflow and keep the client updated."
